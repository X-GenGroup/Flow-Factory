# v0.5.0 implementation and release acceptance

v0.5.0 completes the framework's declared TP/SP/Ulysses-CP paths across the current **19 model
adapters and 14 trainers**. The [user guide](../../guidance/parallelism/README.md) describes the
supported layouts; the [implementation reference](../reference/parallelism/README.md) describes
ownership and numerical obligations. This is a scoped support promise, not a measured Cartesian
product of every model, algorithm, precision, backend and topology.

## Implementation checkpoint

The model stack includes canonical packed TP, model-specific CP, algorithm/state composition,
and the SP completion of dual/single streams, inter-block residuals, refiners, text streams and
eligible output heads. Source docstrings describe local ownership; agent routing selects the
relevant contracts and tests without loading the historical investigation archive at startup.

Review the [current model handoff](../../roadmap/handoffs/v0.5-model-closure.md) and
[SP completion record](../../roadmap/handoffs/v0.5-sp-completion.md) for the PR dependency order,
source identities and evidence. P12, SP completion and P12j are merged through main `bbbdd990`. A merge does

## Evidence retained with the release

- Preserve independent model output/derivative/update oracles and algorithm objective/lifecycle
  proofs. Reuse unchanged owners with an explicit source-delta review; keep fresh and historical
  receipts distinct. A capability declaration alone is not a test result.
- Exercise changed interactions with purposeful local layouts, usually two GPUs for TP and eight
  for DP2 × TP2 × CP2. Cross-node execution and a full model/backend matrix are not additional
  release gates for this scope.
- Preserve async overlap ownership, logical sample/reward counts, valid gradients and updates.
  Ready-order scheduling need not produce bitwise-identical later trajectories. Exact loaded state,
  the first same-state update and each run's subsequent objective/optimizer checks remain separate
  guarantees. Reward-latency hiding and throughput claims require their own measurements.
- Preserve failed candidates and capacity results alongside successful replacements. Small native
  numerical fixtures establish correctness at their stated geometry; they do not establish
  pretrained convergence or unrestricted memory capacity.

## Built-artifact checks

The `Release artifacts` workflow builds the wheel from the source distribution, checks all tracked
runtime Python files and required model resources byte-for-byte, and verifies version, Python floor
and CLI entry points against project metadata. It installs the wheel and then the source distribution
in a clean Python 3.12 environment outside the checkout, resolves all model/trainer registry classes
or checks Bagel's explicit missing-FlashAttention admission error, and invokes all four command-line entry points. Missing optional native kernels remain a separate
model admission boundary; resolving an adapter class is not a generation test.

Reproduce the artifact inspection after `python -m build`:

```bash
python scripts/validate_release_artifacts.py --source . --wheel dist/*.whl \
  --sdist dist/*.tar.gz --report artifacts.json
```

For installed-artifact checks, run `scripts/check_installed_release.py` with the target environment's
Python, `-I`, `--expected-version` and `--report` from outside the checkout. It rejects editable or
external source imports. The CUDA image also installs a built wheel rather than an editable tree.
Actions artifacts retain the package hashes, environment and reports; stable publication must copy
them to durable release assets before those temporary artifacts expire.

The published package version is `0.5.0`. Its stable publication checked source/recipe/tag/package
identity and attached distributions, resolved environments, verification reports and SHA256
checksums as durable GitHub Release assets. PyPI publication is not configured. Use
[publishing](publishing.md) for future releases; a commit-SHA container preview cannot publish
stable aliases. See the [release records](../../roadmap/milestones/v0.5.md#release-records) for
subsequent source-only tags and compatibility work.

The [release-environment qualification](v0.5-validation.md) records installed-artifact hashes,
focused two/four/eight-GPU witnesses and their exact scopes. It is a review record, not a replacement
for the original machine-accepted model/algorithm evidence.

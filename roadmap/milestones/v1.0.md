# v1.0: complete-scope stabilization

Version 1.0 is earned after the 0.x milestones have delivered and qualified the declared scope.
It is not the name of the current baseline and does not imply support for every model/backend/
parallelism combination. The scope includes existing online/offline and multi-role algorithms,
TP/SP/CP, one real MoE model with NCCL EP, optional DeepEP, state recovery, tile-stream reward
overlap, and the developer/agent harness. Deferred research stays in
[the EP milestone's deferred directions](v0.6-v0.7.md#deferred-directions).

## P17: qualify the complete framework and freeze compatibility guarantees

- **Status:** planned
- **Depends on:** [P04](v0.3.md#p04), [P08](v0.4.md#p08), [P14](v0.5.md#p14), [P16](v0.6-v0.7.md#p16); all earlier milestone release criteria must be closed
- **Coordination:** unclaimed
- **Release boundary:** `v1.0.0-rc.1`, followed by `v1.0.0` after stabilization

**Outcome.** Users and contributors have a maintainable, qualified framework with explicit public
contracts, reproducible support evidence and predictable migration requirements.

**Scope.** Integrate the completed milestones, resolve correctness/compatibility findings, remove
superseded ownership and policies, and document the stable extension surface. Inspect the real
owners of topology, preparation, variants/snapshots, algorithm execution, reward scheduling and
state persistence. Simplify where evidence supports it; a new abstraction or a whole-framework
rewrite is not an acceptance requirement. Open separate fix PRs for findings and freeze feature
scope before the RC. Repeat RC tags only when their reviewed contents and evidence warrant it.

**Acceptance.**

- The published capability table covers DDP/ZeRO-2/FSDP2 baseline paths, declared TP/SP/CP paths,
  and the selected EP model/transports. Each claim has concrete dependency, layout and evidence
  boundaries; unsupported EP x TP x CP combinations remain explicit.
- Representative online, offline, multi-role, reference/EMA/snapshot and reward-overlap paths
  retain their mathematical and lifecycle contracts. Supported state continuation proves the
  next update, not only that a checkpoint loads. Remaining excluded combinations are documented.
- Hooks and CPU CI are reproducible from a fresh checkout/worktree. The diff planner selects
  required distributed evidence without a fixed 45-cell campaign or fixed reward deployment;
  required missing or stale evidence prevents a qualified result.
- Shared contracts have one authoritative owner and documented extension entry points. No
  competing preparation path, state-copy mechanism, test catalog or validation policy remains
  merely for historical compatibility; necessary adapters have a stated lifetime and owner.
- Public configuration, extension, checkpoint and dependency compatibility guarantees are
  explicit. Required migrations from 0.x are documented and tested. New public breaking changes
  after 1.0 require a major-version decision rather than an incidental refactor.
- Targeted qualification covers critical interactions, selected actual weights and repeated-iteration
  resource cleanup within eight local GPUs. Cross-node execution is not an additional default
  gate for unchanged upstream transports; specific cross-node performance claims need their own evidence. Performance claims use
  a stated workload; arbitrary capacity/performance targets are not correctness gates.
- RC findings are resolved or explicitly outside the supported scope. The final integration
  commit has traceable required evidence, aligned package metadata/changelog, installation and
  migration instructions, and release records. An RC result is reused only with a justified
  comparison to the actual final commit.

## Release records

Not released. Record the RC tag(s) and final v1.0.0 with immutable commits, artifacts, tested
dependency tuples, supported capabilities and exclusions. Use package `1.0.0rc1` for Git tag
`v1.0.0-rc.1`, then package `1.0.0` for the stable tag. Earlier 0.x source tags remain immutable.
After v1.0, ordinary fixes use patch releases and compatible additions use minor releases; new
research directions receive their own work items and evidence before entering supported scope.

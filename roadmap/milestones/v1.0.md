# v1.0: release baseline

Establish a named baseline for current online/offline training before the new distributed releases.
See the [roadmap index](../README.md) for the dated starting evidence and later milestones.

<a id="p00"></a>
## P00: establish the baseline release

- **Status:** planned
- **Depends on:** none
- **Coordination:** unclaimed
- **Release boundary:** `v1.0.0`

**Outcome.** Contributors and users can identify the supported starting behavior, version metadata,
and compatibility boundary before TP/SP and CP are introduced.

**Scope.** Prepare the release from stable main, using inspected commit `2a115133` as a starting
candidate rather than treating an unmerged TP branch as the baseline. Align package metadata,
changelog, supported backend/configuration documentation, and known limitations. Existing
`v0.1.0` remains immutable. Recheck tags before release preparation; if an existing `v1.0.0` is
identified, reference it and revise later targets instead of creating or moving a duplicate tag.

**Acceptance.**

- Version metadata and the release record agree on the target commit and capabilities.
- Existing online, offline, multi-role and overlap capabilities are distinguished from planned
  work. Unsupported checkpoint/backend combinations are stated explicitly.
- Evidence is traceable to the source it tested; a later green run does not certify an older
  historical commit. Select any missing checks by the actual release diff and claimed behavior.
- Tag the reviewed release-preparation commit, which may follow the original baseline candidate
  to carry consistent version metadata.

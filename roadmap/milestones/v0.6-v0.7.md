# v0.6-v0.7: MoE and expert parallelism

Build on the qualified [v0.5 boundary](v0.5.md). EP does not block that CP checkpoint, but P15/P16
are included in the later [v1.0 qualification](v1.0.md). Select one actual MoE
model before introducing its routing and expert-state abstractions; dispatch transport alone is
not a complete training integration.

<a id="p15"></a>
## P15: implement one MoE model with NCCL EP

- **Status:** planned
- **Depends on:** [P14](v0.5.md#p14)
- **Coordination:** unclaimed
- **Release boundary:** `v0.6.0`

**Outcome.** A real MoE model trains correctly with distributed experts and a reproducible reference
implementation based on PyTorch/NCCL all-to-all.

**Reference candidates (user-selected, 2026-11-05).** Use
[DiT-MoE](https://github.com/feizc/DiT-MoE) as the initial model family, specifically
`DiT-MoE-XL/2-8E2A` and `DiT-MoE-G/2-16E2A`. The upstream README lists both as 256x256
rectified-flow checkpoints. Before integration, pin source and weight revisions and inspect
class conditioning, scheduler/CFG, router, shared/routed experts and combine semantics. Preserve
the same deterministic expert-combination order in rollout and replay for coupled algorithms.
These are future reference models, not current adapter/EP support; v0.5 implements no EP.

**Scope.** Preserve the selected model's router semantics, token/expert identity and
dispatch/combine behavior. Define expert placement, dense versus expert parameter groups,
optimizer ownership, auxiliary losses where applicable, and checkpoint storage. Start with the
smallest declared EP configuration rather than promising every TP/CP combination.

**Acceptance.**

- Compare outputs, gradients and updates with an unsharded reference, including uneven routing,
  empty destinations and any capacity/drop behavior the model actually defines.
- Fixed-topology save/restore preserves expert identity, optimizer state and the next update.
- Document the actual mesh/groups and dense/expert reduction semantics; do not assume EP is an
  independent multiplier of every existing mesh axis.
- If the model uses expert-choice routing over tokens, prove its global selection semantics
  before enabling CP. Otherwise EP + CP remains explicitly unsupported.

<a id="p16"></a>
## P16: add DeepEP as an optional transport

- **Status:** planned
- **Depends on:** [P15](#p15)
- **Coordination:** unclaimed
- **Release boundary:** `v0.7.0`

**Outcome.** Supported hardware can use DeepEP without changing the selected model's mathematical
contract, while NCCL remains the correctness reference and supported fallback.

**Scope.** Pin a DeepEP version and its hardware/software requirements. Implement it behind the
same dispatch/combine boundary as P15. Select transport consistently across ranks at startup;
switching implementations after a collective partially fails is not a recovery strategy.

**Acceptance.**

- Forward, backward and optimizer behavior agree with the NCCL reference under justified
  tolerances for the selected precision and routing workload.
- Initialization, rank agreement, asynchronous buffer ownership, failure propagation and cleanup
  are verified; repeated iterations remain bounded.
- Report measured benefits with an environment and workload, and test the supported startup
  fallback instead of merely documenting it.

## Deferred directions

These are future design questions, not additional conditions for v1.0 or automatic support claims.
Assign new stable IDs when a concrete proposal and acceptance boundary are ready.

| Direction | Required decision or proof |
|---|---|
| CP transports beyond the qualified v0.5 matrix | Further transport/layout proofs; the bounded Ring work needed for v0.5 coverage belongs to P12 |
| Layouts beyond the qualified v0.5 matrix | P12 owns existing-model padding/masking/packed needs; further layouts require separate proofs |
| Additional CP/EP model families | Real adapter structure and checkpoint/conditioning evidence |
| EP + CP/TP composition | Actual router semantics and dense/expert group interactions |
| Cross-topology optimizer resharding | Explicit distinction from weight-only restart and fixed-topology exact resume |
| Arbitrary in-flight tile recovery | Serializable pending work, schedule order and external feedback identity |
| Concurrent rollout and training | Independent versioned execution state and algorithm-specific staleness policy |

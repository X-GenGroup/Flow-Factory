# v0.4: explicit runtime ownership

Build on completed [v0.3](v0.3.md) capabilities and evidence. Preserve existing configuration and
extension behavior while clarifying the existing mechanisms described in
[architecture direction](../design/architecture.md). The CP feasibility probe begins during P06;
production CP releases wait for this milestone's acceptance.

<a id="p05"></a>
## P05: unify topology and logical sample geometry

- **Status:** in_progress
- **Depends on:** [P03](v0.3.md#p03)
- **Coordination:** implementation in `feat/p05-topology`; awaiting review and merge

**Outcome.** Sampling, rewards, optimization and state identity agree on the difference between
physical ranks and logical data replicas.

Implementation: [parallelism geometry](../../guidance/parallelism.md) describes the shared topology
contract, unchanged CP=1 checkpoint identities and isolated CP geometry probes. Production CP
remains disabled; these probes do not qualify model CP execution.

**Scope.** Consolidate the merged [distributed scope helpers](../../src/flow_factory/utils/dist.py),
[parallelism arguments](../../src/flow_factory/hparams/parallelism_args.py) and
[runtime identity](../../src/flow_factory/trainers/common/runtime_identity.py) around one topology
contract. PR #270 already separates physical world size from logical DP and scopes data, RNG,
rewards and reductions; extend that authority for CP rather than reimplementing it. Represent
TP/CP groups, data placement and feedback/statistics scopes explicitly. Replace duplicated world
size arithmetic at authoritative owners and update every reached registry implementation.

**Acceptance.**

- Tests verify group members and sample identities: the same TP x CP group shares a sample while
  logical data replicas receive the intended distinct data.
- Batch sizes, group statistics and reductions use the correct scope and retain feature-disabled
  behavior across affected backends.
- Configurations fail with concrete dimensions before heavyweight allocation when invalid.
- New internal structure keeps existing public configuration semantics compatible.

<a id="p06"></a>
## P06: establish one model-preparation owner

- **Status:** planned
- **Depends on:** [P05](#p05)
- **Coordination:** unclaimed

**Outcome.** Loading, variants, precision, attention, parallel transforms, backend preparation and
compilation have an explicit order and one owner for each mutation.

**Scope.** Refine the existing preparation path; retain Accelerate for existing backends. Use a
small Wan CP probe to test whether Diffusers hooks and the FSDP2 mesh can be bridged without
competing CP preparation. Record the tested dependency tuple and unsupported combinations.
Preserve the merged ordering: variant materialization and LoRA injection, TP/SP transforms,
backend preparation, parameter rebinding, then snapshots. TP applies to every declared variant
route and de-duplicates shared module identities. Assess H3's materialization peak separately;
any meta/sharded-loading implementation needs its own bounded change and validation before H3 TP
can be advertised. It is not solved by enabling SP or changing a test canvas.

**Acceptance.**

- Modules are neither prepared nor sharded twice; parameter/optimizer identities and component
  routes remain valid after preparation.
- Attention selection and CP setup obey the selected upstream implementation's requirements;
  train and inference receive compatible transforms.
- The CP probe supplies concrete evidence for the bridge and is retained as a reproducible test
  when it becomes part of P09.
- If the bridge is insufficient, record the failing contract and add a bounded native-FSDP2
  implementation item before committing to it. A full Accelerate replacement is not a dependency.

**P06 bridge decision.** The [bounded Wan probe](../../guidance/model_preparation.md#bounded-cp-bridge-result)
retains Accelerate FSDP2 and uses Diffusers alone for native Ulysses2 CP hooks. It compares every
gradient, update and optimizer state on DP2 x CP2. Full-output mean loss needs CP normalization
because the gather backward returns local token contributions and FSDP averages DP x CP.
P09 must make that reduction contract explicit and select attention before CP hook installation;
this result does not enable public CP or qualify TP+CP, resume, other models or cross-node use.
A full Accelerate replacement is not required by this probe.

<a id="p07"></a>
## P07: define parameter-state updates and persistence

- **Status:** planned
- **Depends on:** [P06](#p06)
- **Coordination:** unclaimed

**Outcome.** Trainable variants, fixed references, EMA and named snapshots have explicit identities,
writers, lifetimes, update cadence and checkpoint behavior.

**Scope.** Extend ModelBundle/variants/snapshots rather than adding a competing copy-management
system. Basic TP model/optimizer round trips and in-memory DTensor snapshot updates already exist.
Complete the missing persistence of EMA/reference/algorithm snapshots under FSDP2/TP instead of
replacing the working checkpoint mechanism. Keep backend-aware storage separate from algorithm
role names and update semantics.

**Acceptance.**

- Frozen states have no optimizer gradients but can change through their declared copy/EMA
  operation; update frequency is exercised rather than left dormant by a short test.
- Inactive role parameters and existing optimizer moments do not change during another role's
  update. Snapshot use restores the live state and preserves train-inference consistency.
- Supported fixed-topology resume restores state and produces the same next update as continuous
  execution within justified precision tolerances.
- Existing supported checkpoint/configuration formats remain compatible or receive an explicit
  migration; unsupported combinations fail before partially mutating loaded state.

<a id="p08"></a>
## P08: clarify algorithm and tile-stream lifecycles

- **Status:** planned
- **Depends on:** [P07](#p07)
- **Coordination:** unclaimed
- **Release boundary:** `v0.4.0`, after P05-P08 are complete

**Outcome.** The shared runtime owns acquisition, feedback readiness and optimization lifecycle;
algorithms own their objective and role-update semantics.

**Scope.** Consolidate existing ExecutionContract, feedback/overlap contracts and role coordination
into their authoritative paths. Preserve the complete-rollout policy-version boundary while
rewards execute asynchronously and overlap optimization. Make tile, request batch, accumulation
window and optimizer-step boundaries explicit. Remove duplicated branching only after behavior is
captured by focused evidence.
Keep #274's worker-device selection and #270's peer reward agreement/collective settling intact.
Treat decode sharing across TP peers as a separate optimization with ownership and timing proof;
it is not necessary to move decoding merely to clarify the tile lifecycle.

**Acceptance.**

- Representative dataset/no-feedback, generation/no-feedback and generation/runtime-reward paths
  retain their mathematical behavior and counters.
- Multiple controlled tiles exercise ordered/ready schedules, source identity, closure statistics,
  role cadence, backpressure, cancellation and failure cleanup.
- Repeated iterations bound live resources; checkpoint boundaries handle pending feedback and
  schedule order explicitly.
- Scheduling traces prove functional overlap. Any claim of fully hidden reward latency is backed
  by a separate timing experiment with a stated workload.
- Existing APIs remain compatible or receive an explicit migration. Concurrent rollout and
  parameter updates are not introduced implicitly by this refactor.
